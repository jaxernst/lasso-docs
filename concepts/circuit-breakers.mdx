---
title: Circuit breakers
description: How RPC Core takes a failing provider transport out of rotation and tests it before returning it.
---

Circuit breakers temporarily exclude failing upstream transports and admit recovery attempts before returning them to ordinary routing. HTTP and WebSocket health are tracked separately.

| State | Meaning |
| --- | --- |
| Closed | Normal admission, subject to the other routing gates. |
| Open | Ordinary traffic is excluded until recovery is permitted. |
| Half-open | Limited recovery traffic determines whether service has recovered. |

Connection state, rate-limit cooldowns, lag, method restrictions and request parameters can exclude a provider even when its circuit is closed.

## Connection failures

When an HTTP endpoint refuses connections, three failed connection attempts open
its circuit. The first recovery test comes after 1 second, and each failed test
doubles the wait up to 4 seconds, plus jitter. One successful request closes the
circuit, so a recovered endpoint is back in rotation within seconds. While it is
half-open, the endpoint keeps its usual place in the strategy's order, so ordinary
traffic tests it even when background observations are off. Subscription replay
works normally during that time.

Chain-identity probes record identity and health; routed requests and head polls
decide when a circuit opens and recovers.

## Timeouts

A request timeout is neutral to the circuit on its own — it shows only that a
provider was slower than that attempt's share of one request's budget. It asks
the health prober to check that instance on its next tick instead. The
prober runs one probe of an instance at a time and counts consecutive probe
timeouts; at two (five seconds each) it opens the HTTP circuit, so an upstream
that accepts requests and never answers leaves rotation. A probe success
resets only that count, and no other probe outcome reaches the breaker.
Routed requests and head polls still drive its recovery.

## Refusals that leave the circuit closed

Some refusals say nothing about a provider's health, so they never count toward
its circuit:

- HTTP 429, a rate limit.
- HTTP 402, a spent plan allowance.
- HTTP 406 with a body that isn't a JSON-RPC error: a gateway refusing the
  request before its RPC handler runs.

Lasso moves the request to the next eligible provider. A 429 or 402 also
starts a [cooldown](#rate-limit-cooldowns). A 406 affects only the request it
refused, so the provider keeps serving its other methods.
See [error codes](/api/error-codes#rate-limits-and-spent-allowances) for what
the client receives when every provider refuses.

## Rate limits and shared providers

Rate-limit backoff is a separate signal from circuit failure. A provider can be temporarily rate limited while its circuit remains closed. Identical upstreams shared across profiles share runtime signals; creating another profile does not bypass the provider's real quota.

To stay under a provider's published limit before it starts refusing, give it an
[outbound request budget](/configuration/providers#outbound-request-budget). A
spent budget sends nothing, so it never opens a circuit or starts a cooldown.

### Rate-limit cooldowns

An HTTP 429 or 402 moves the provider behind healthy ones for as long as it asks.
Lasso reads the delay in this order:

1. A `Retry-After` header, in seconds or as an HTTP date.
2. `data.retry_after_ms` in the JSON-RPC error body.
3. `data.retry_after` in whole seconds. Values with units, such as `120ms`, are ignored.
4. A delay in the error message, such as `Try again in 120 seconds`.

Without any of these, the default cooldown is 30 seconds. Every delay is capped
at ten minutes. A zero or past `Retry-After` falls through to the body hint or
the default, so it can't send traffic straight back to a provider that is still
refusing. Lasso keeps the refusal's JSON-RPC code and up to 1,000 bytes of its
message, and discards the rest of the body. A quota refusal keeps its longer
cooldown.

Inspect the affected transport and region. An aggregate warning may represent only part of the deployment. Do not interpret a regional problem as proof that every region is unavailable.

## Configuration

### Circuit Breaker Defaults

```elixir
config :lasso, :circuit_breaker,
  failure_threshold: 5,     # Aggregate failure threshold; category thresholds also apply
  success_threshold: 2,     # Consecutive successes to close
  recovery_timeout: 60_000  # Base ms before half-open; category/backoff rules also apply
```

Circuit settings take effect when provider instances start; restart Lasso after changing application configuration. YAML reload does not restart existing circuit breakers.
