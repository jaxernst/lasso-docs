---
title: Block height monitoring
description: How RPC Core observes upstream heads and uses them in routing.
---

RPC Core tracks each provider's block height so routing can steer around
lagging providers. It polls each upstream over HTTP and, when enabled and
connected, also receives `newHeads` over WebSocket.

For request-level monotonicity, use [Block regression protection](/advanced/block-continuity).
For related state reads at one block, use [Read at one block](/advanced/read-at-one-block).

## HTTP and WebSocket observations

Each physical upstream instance has one block-sync worker for a chain, even
when multiple profiles refer to it. The worker stores height, observation time,
and source in the block-sync registry. Profiles sharing that instance also share
its observations.

HTTP `eth_blockNumber` polling follows the shortest positive head interval
requested by enabled references. `monitoring.http_heads_interval_ms` and
`http_backup_interval_ms` separate normal polling from polling while WebSocket
evidence is fresh; legacy `probe_interval_ms` supplies their fallback defaults.
`background_observations: false` disables that reference's periodic work, and
`0` disables an individual interval. Other references to a shared upstream can
still request observations. Client requests can supply evidence independently.
See [monitoring settings](/configuration/profiles#monitoring).

The chain-level `websocket.subscribe_new_heads` setting defaults to `true`.
Providers inherit it unless they set their own `subscribe_new_heads` value.
A usable WebSocket connection is also required. See [Profile configuration](/configuration/profiles)
and [Provider configuration](/configuration/providers).

## Comparing heights

Core ignores stale observations when deriving its chain reference height.
With a measured block interval, it may give a bounded credit to an older
observation before comparing heights. The reference is selected from the
current, aligned provider samples; it is an operational routing estimate, not
a consensus vote or proof of the canonical chain.

Unknown or stale data must not be read as verified head agreement. The
dashboard's `monitoring.lag_alert_threshold_blocks` is a separate status
threshold; it does not set a routing limit.

The measured block interval uses an exponential moving average of increasing
heights. Until five valid samples are available, Core uses the configured
`block_time_ms` fallback. This helps account for observation delay on fast
chains, but it cannot turn a stale or incorrect upstream response into a
verified block.

## Head freshness

A request that needs the chain's moving head prefers routes with fresh
evidence that they are at it. What a request needs comes from its own
parameters: a `latest` selector, an omitted range upper bound, an omitted
optional selector that a client resolves to its current state (such as
`eth_call` or `eth_getBalance`), and a replay-safe read with no block
parameter all need the moving head; a numeric selector needs that block;
block hash, `earliest`, `safe`, `finalized`, `pending`, writes and
subscriptions need nothing.

Each route's latest HTTP and WebSocket head observation is compared with the
highest fresh observation across the profile, less an agreement band — the
blocks the chain produces in two seconds at its `block_time_ms`, bounded
between 1 and 20 blocks, crediting the blocks a route could have produced
since its own observation. A route proven short of that target, or one
reporting the agreed height on a different block hash, is deferred behind the
others in its health tier. Deferral never excludes a route: when every
current route fails or lacks the method, a lagging one still serves, and a
route a few blocks behind still serves historical reads. `selection.max_lag_blocks`
was removed in v0.9.0 in favor of this automatic, per-chain behavior; a
profile that still sets it keeps loading, but the field has no effect.

## Health probes

The probe coordinator checks upstream HTTP identity and health separately from
block-height polling. Its 200 ms tick schedules work; it does not probe every
provider five times per second. The effective provider cadence follows the
shortest positive identity interval requested by enabled references, with
failure backoff and jitter. `chain_identity_interval_ms` can disable identity
probing without disabling head observations. A matching `eth_chainId` probe can restore an HTTP
endpoint previously rejected for an identity mismatch. See [Provider selection](/concepts/provider-selection)
for the remaining admission checks.

## Operating guidance

- Configure `probe_interval_ms`, `block_time_ms`, and lag limits for the chain's
  actual cadence and your workload. Sharing a provider across profiles can
  change its effective polling cadence.
- Compare provider heights and freshness by region before treating lag as a
  provider fault. A quiet log stream alone is not evidence of a dead connection.
- Verify a representative upstream-backed request; a healthy application
  endpoint does not prove that every provider is usable.
