# Versions and evidence

**Lasso RPC Core** is the routing engine you run and protect yourself.
**Lasso Cloud** runs the same engine as a managed service, with accounts, keys,
billing and managed providers. Cloud deploys on its own schedule, so its
behavior can be ahead of the latest Core release; this page shows where.

## Core and Cloud by workload

| Capability | RPC Core v0.7.0 | Lasso Cloud |
| --- | --- | --- |
| HTTP reads and batches | Routed over the upstreams you configure | Routed over managed pools or your Custom profiles |
| Signed transactions | One upstream dispatch | The same bytes to up to three providers in turn; sender faults stop at the first ([details](/cloud/rpc-behavior#transactions)) |
| WebSocket `newHeads` and `logs` | Shared upstream streams with bounded failover and backfill | The same, on every account |
| Historical state and logs | Declared capabilities plus learned depth and log-range limits that reorder providers ([learning](/concepts/provider-learning)) | Steered toward providers known to serve that history |
| HTTP filters | Forwarded to one provider, without failover | Rejected with `-32601`; use `eth_getLogs` or subscriptions |
| Block regression protection | Opt-in per profile, with optional fleet coordination | On or off per Custom profile chain |
| Client authentication and quotas | Bring your own, at your network or reverse proxy | Keys, rate limits, balances and usage |
| Funding | Not applicable | USDC top-ups over x402 or MPP, and Custom access by the day |

Whichever you run, provider plans set the ceiling on history, methods and
quota, so qualify your real application flow before moving traffic; the
[trial guide](/cloud/bring-your-own-rpc) shows how. The method contracts are
in [Core supported methods](/api/supported-methods) and
[Cloud RPC method behavior](/cloud/rpc-behavior).

## Core releases

Full notes are on [GitHub releases](https://github.com/jaxernst/lasso-rpc/releases).

| Release | Highlights | Upgrade notes |
| --- | --- | --- |
| [v0.7.0](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.7.0) | Learned method refusals, historical depth and `eth_getLogs` range limits are on by default: matching providers are moved behind alternatives. Includes a [Chainstack template](/configuration/providers#chainstack-template) | Routing order can change. Set `LASSO_PROVIDER_KNOWLEDGE_METHOD_REFUSAL_MODE`, `LASSO_PROVIDER_KNOWLEDGE_HISTORICAL_DEPTH_MODE` and `LASSO_PROVIDER_KNOWLEDGE_SPAN_LIMIT_MODE` to `off` to keep v0.6.0 ordering. Capability list fields left as YAML `null` now fail validation; use `[]`. No migrations |
| [v0.6.0](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.6.0) | `latency-weighted` is now `balanced-fast`, and `priority` has its own HTTP and WebSocket routes. `load-balanced` gives each physical upstream one first-pick share. Bare `/api/ready` reports replica readiness, so a dead upstream no longer takes every replica out of service. Bounded selection diagnostics name why a request found no eligible provider | Rename `LW_BETA` to `BALANCED_FAST_BETA`; the old name isn't read. `latency-weighted` URLs and `strategy` values keep working as permanent aliases. Load balancers that need upstream-backed readiness use `/api/ready?profile=PROFILE&chain=CHAIN` |
| [v0.5.1](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.5.1) | A full Prometheus `/metrics` contract with per-route totals, latency histograms, attempt diagnostics, circuit, WebSocket and BEAM series, and a refreshed Grafana dashboard. Opt-in OpenTelemetry tracing (`LASSO_OTEL_ENABLED`) with W3C propagation and log correlation. Fixes a provider staying ineligible after its first 429 until restart | Upgrade if your providers return 429s. Prometheus consumers should review the new metric families and the `transport`, `profile` and `origin` labels |
| [v0.5.0](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.5.0) | Route readiness, node-local Prometheus metrics, JSON console logs, profile validation and reload commands, standalone provider discovery and routing evidence. Tighter HTTP and WebSocket resource limits | Stricter request and discovery validation can reject malformed input that earlier versions accepted |
| [v0.4.5](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.4.5) | Phoenix, Cowboy, Cowlib and Ranch upgrades (Cowlib 2.20.0 resolves `CVE-2026-43971`). Correct Public Arbitrum archive routing. Requests no provider can serve fail at admission with a structured [`reason`](/api/error-codes#core-routing-exhaustion) | Review local archival declarations against your historical state reads |
| [v0.4.4](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.4.4) | `load-balanced` tries distinct physical providers before a second transport of the same one ([details](/concepts/routing-strategies#load-balanced)) | None |
| [v0.4.3](https://github.com/jaxernst/lasso-rpc/releases/tag/v0.4.3) | Rejects an HTTP endpoint whose chain-ID probe mismatches, orders orphan-log events correctly, and strips URL credentials and paths from provider diagnostics | None |

None of these releases needs a profile or journal migration.

## Container verification

Each release's container is verified on native Linux AMD64 and ARM64 runners
after an anonymous pull and signed-attestation check. The v0.7.0
[verification summary](https://github.com/jaxernst/lasso-rpc/releases/download/v0.7.0/container-verification.md)
records 23 checks per image
([AMD64](https://github.com/jaxernst/lasso-rpc/releases/download/v0.7.0/verification-amd64.json),
[ARM64](https://github.com/jaxernst/lasso-rpc/releases/download/v0.7.0/verification-arm64.json))
covering controlled upstream requests, HTTP failover, WebSocket RPC and `newHeads`
delivery, configuration reload, history across container replacement and
read-only profile mounts. The
[published quickstart check](https://github.com/jaxernst/lasso-rpc/releases/download/v0.7.0/quickstart-published.json)
downloaded the release Compose attachment and passed live `eth_blockNumber`
requests on six configured chains. These are finite release checks, not a
capacity guarantee. Verify the attestation
yourself with:

```bash
gh attestation verify oci://ghcr.io/jaxernst/lasso-rpc@sha256:0ede906c950526de24183423c4a3d43e717fdeaebb52c5630ee336fb9054f984 --repo jaxernst/lasso-rpc
```

## Routing benchmark

Lasso's routing engine adds 0.70 to 1.08 ms at p95 across five trials at
10,000 requests per second against a synthetic provider, and 2.29 ms in a
separate 60-second instrumented run. See the
[routing overhead benchmark](/cloud/routing-overhead), the
[full report](https://lasso.sh/benchmarks/routing-overhead.html) and the
[raw evidence](https://lasso.sh/benchmarks/lasso-routing-overhead-ledger-2026-08-24.tar.gz).
