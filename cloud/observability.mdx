# Routing evidence

Every Lasso response tells you what served it and what it cost, and one query
parameter adds which provider answered and why. Use this page to debug a slow
or failed request, explain a bill, or prove a routing change worked.

```bash
curl -sS -D - "$LASSO_RPC_URL/fastest/base?include_meta=body" \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
```

```http
x-lasso-request-id: 01J9Z…
x-lasso-access: premium
x-lasso-cu: 2
x-lasso-usd: 0.00001
x-lasso-balance-usd: 19.87421
```

```json
{
  "jsonrpc": "2.0", "id": 1, "result": "0x3157d37",
  "lasso_meta": {
    "strategy": "fastest", "chain_id": 8453,
    "candidate_providers": ["premium/premium_base_2:http", "premium/premium_base_1:http"],
    "selected_provider": { "id": "premium_base_2", "protocol": "http" },
    "upstream_latency_ms": 9.4, "lasso_overhead_ms": 1.9, "retries": 0
  }
}
```

## Where evidence lives

| Surface | What it tells you | How to get it |
|---|---|---|
| Response headers | Request ID, serving access, fallback, size, charge, balance, rate limit | On every response |
| `lasso_meta` | Strategy used, candidates, the provider that served it, latency split, retries | `?include_meta=body`, or `?include_meta=headers` for a base64url `x-lasso-meta` header that leaves the body untouched |
| Key view | Requests and charges over the last 24 hours, and recent errors grouped by code and provider with a `next_action` | `GET /api/v1/keys/{id}`, or `/api/v1/keys/current` with the RPC key |
| Account view | Balance, serving access, fallback, included usage, rate limits | `GET /api/v1/accounts/{id}` |
| Account page | 30-day request and CU charts by profile, each key's traffic share and per-profile usage, included usage and balance spend | [lasso.sh/account](https://lasso.sh/account) |
| Dashboard | Chains, providers, health and latency by region, and recent activity | [lasso.sh/dashboard](https://lasso.sh/dashboard) |

Every header, metadata field and error code is listed in
[response signals and errors](/cloud/reference/signals-and-errors). The
routing engine's metadata fields are defined once, in
[request metadata](/observability/request-metadata).

## Debug a request

1. Capture `x-lasso-request-id` at your client.
2. Check `x-lasso-access` and `x-lasso-fallback`: was it served where you
   expected, and if not, why?
3. Read `lasso_meta`: which strategy applied, which providers were candidates,
   which one served it, and how many retries it took.
4. For an error Lasso originates, read `error.data.code` and
   `error.data.next_action`; they name the fix. Provider errors keep their
   code and message.
5. Check the key's `recent_errors` and the dashboard's provider health for a
   pattern across requests.

When something in Lasso is confusing or broken, report it, quoting the request
ID:

```http
POST https://lasso.sh/api/v1/feedback
Content-Type: application/json

{"message": "eth_getLogs on base returned -32005 for a 500-block range", "category": "rpc", "request_id": "01J9Z…"}
```

See [agent entry points](/cloud/reference/agent-entry-points#feedback) for
the fields.

## Limits

- Managed providers appear under public aliases such as `premium_base_2`;
  Custom profiles show your own provider names.
- `candidate_providers` lists the order considered, not the attempts. Use
  `selected_provider` and `retries`.
- An HTTP batch's `x-lasso-meta` header describes one item. Use
  `include_meta=body` to see every item's evidence.
- Usage views summarize activity for insight; the account balance is the
  record of money.
- The dashboard's recent activity is a live stream, not a request log.

## Understand latency

`lasso_meta` timings measure work inside Lasso, including upstream calls. They
exclude client network RTT, TCP/TLS setup, edge routing, and response delivery.
Reuse connections with HTTP keep-alive or HTTP/2. In a production Base
`eth_blockNumber` measurement on October 29, 2026, median client latency was
119 ms with a fresh connection versus 42 ms reused; metadata reported 13 ms.
These are measurements from one client location, not a latency guarantee.
The public tier uses free providers and has a wider latency tail than premium.
