# Routing evidence

Every Lasso response tells you what served it and what it cost, and one query
parameter adds where it went and why. Use this page to debug a slow or failed
request, explain a bill, or prove a routing change worked. Responses stay
standard JSON-RPC unless you ask for more.

```bash
curl -sS -D - "$LASSO_RPC_URL/fastest/base?include_meta=body" \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
```

```http
x-lasso-request-id: 01J9Z…
x-lasso-access: premium
x-lasso-cu: 2
x-lasso-usd: 0.000010
x-lasso-balance-usd: 19.874210
```

```json
{
  "jsonrpc": "2.0", "id": 1, "result": "0x3157d37",
  "lasso_meta": {
    "strategy": "fastest", "chain_id": 8453, "access": "premium",
    "candidate_providers": ["premium_base_2:http", "premium_base_1:http"],
    "selected_provider": { "id": "premium_base_2", "protocol": "http" },
    "upstream_latency_ms": 9.4, "lasso_overhead_ms": 1.9, "retries": 0
  }
}
```

## Where evidence lives

| Surface | What it tells you | How to get it |
|---|---|---|
| Response headers | Request ID, serving access, fallback, size, charge, balance, rate limit | On every response |
| `lasso_meta` | Strategy used, candidates, the provider that served it, latency split, retries | `?include_meta=body`, or `?include_meta=headers` for a base64url `x-lasso-meta` header that leaves the body untouched |
| Key view | Requests and charges over 24 hours, and recent errors grouped by code and provider with a `next_action` | `GET /api/v1/keys/{id}` |
| Account view | Balance, serving access, fallback, included usage, rate limits | `GET /api/v1/accounts/{id}` |
| Dashboard | Chains, providers, health and latency by region, and recent activity | [lasso.sh/dashboard](https://lasso.sh/dashboard) |

Every header, metadata field and error code is listed in
[response signals and errors](/cloud/reference/signals-and-errors). The
routing engine's metadata fields are defined once, in
[request metadata](/observability/request-metadata); Lasso Cloud adds
`access` and `fallback`.

## Debug a request

1. Capture `x-lasso-request-id` at your client.
2. Check `x-lasso-access` and `x-lasso-fallback`: was it served where you
   expected, and if not, why?
3. Read `lasso_meta`: which strategy applied, which providers were candidates,
   which one served it, and how many retries it took.
4. For an error, read `error.data.code` and `error.data.next_action`; they name
   the fix.
5. Check the key's `recent_errors` and the dashboard's provider health for a
   pattern across requests.

When something in Lasso is confusing or broken, report it, quoting the request
ID:

```http
POST https://lasso.sh/api/v1/feedback
Content-Type: application/json

{"message": "eth_getLogs on base returned -32005 for a 500-block range", "category": "rpc", "request_id": "01J9Z…"}
```

Reports go to the people who operate Lasso. See
[agent entry points](/cloud/reference/agent-entry-points#feedback).

## Limits

- `lasso_meta` shows which provider served a request, not that its answer was
  correct.
- Managed providers appear under public aliases such as `premium_base_2`;
  Custom profiles show your own provider names.
- A candidate list isn't a list of attempts. Use `selected_provider` and
  `retries`.
- An HTTP batch's `x-lasso-meta` header describes one item. Use
  `include_meta=body` or individual requests when you need every item's
  evidence.
- `x-lasso-balance-usd` is the serving machine's view; machines reconcile
  within about 10 seconds. The account view is authoritative.
- Key usage and recent errors are best-effort diagnostics over 24 hours, not a
  billing ledger. The dashboard's recent activity is a live stream, not a
  request log.
