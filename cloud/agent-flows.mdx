---
title: Operate RPC with an agent
description: Create a recoverable endpoint, top it up with prepaid credit, hand it to its owner, and manage custom profiles over HTTP.
---

An agent can run the full endpoint lifecycle over Lasso's HTTP management API
with its existing HTTP tools. No SDK or CLI is required. The operational
reference for agents is [`/SKILL.md`](https://lasso.sh/SKILL.md).

<Note>
The management API is in preview. Check live availability before following a
recipe: `payments.prepaid` and `auth.claiming` in
[`/agent.json`](https://lasso.sh/agent.json), and operation flags in the
[configuration schema](https://lasso.sh/api/v1/management/configuration-schema).
[`/openapi.json`](https://lasso.sh/openapi.json) has the exact request and
response schemas.
</Note>

Three credentials stay separate: the **RPC key** goes in the application's
secret store, the **management credential** stays with the agent, and **wallet
authority** stays with the user's signer. None substitutes for another.

Before every mutation, persist its `Idempotency-Key` UUID, exact body and
credential. After a timeout or lost response, replay the same request. A new
UUID or credential starts new work instead of recovering the original.

## Create a managed endpoint

Generate and persist a management credential (`lasso_mk_` followed by 32 random
bytes as unpadded base64url) and a UUID, then create the app:

```http
POST /api/v1/management/keys
Authorization: Bearer <management credential>
Idempotency-Key: <UUID>
Content-Type: application/json

{"name":"trading-bot"}
```

The default grant is `keys:read`, `keys:write` and `claims:create`. If the app
will buy credit, request funding up front:

```json
{
  "name": "funded-bot",
  "permissions": ["keys:read", "keys:write", "claims:create", "funding:read", "funding:write"]
}
```

Save `data.key_id` and `data.credential_delivery.secret`. Build the RPC URL from
`credential_delivery.rpc_url_template` by replacing `{chain}`:

```text
https://lasso.sh/rpc/k/<secret>/load-balanced/{chain}
```

`strategy_url_template` also exposes `{strategy}`; valid values are in
`route_parameters`. The `endpoint` field is only a base URL and returns `422
rpc_route_required` if called directly.

`GET /api/v1/management/keys/<key_id>` inspects the key without returning its
secret.

## Top up with prepaid credit

Prepaid credit buys premium RPC usage on the same key and URL. Rails are USDC.e
on Tempo (`mpp`) and USDC on Base (`x402`), each capped per quote at the
`maximum_quote_usd` in `/agent.json`. Use the user's approved budget and a
separately authorized wallet.

<Steps>
  <Step title="Quote">
    ```http
    POST /api/v1/management/keys/<key_id>/funding-operations
    Authorization: Bearer <management credential>
    Idempotency-Key: <UUID>
    Content-Type: application/json

    {"rail":"x402","amount_usd":"1","max_usd":"1","payer":"<wallet address>"}
    ```

    Save `data.id`. Check the network, asset, recipient, amount and credited CU.
    A quote does not move money.
  </Step>
  <Step title="Pay">
    `POST /api/v1/management/funding-operations/<id>/pay` returns 402 with the
    payment challenge. The wallet signs it, then repeat `/pay` with the signed
    credential:

    | Rail | Management auth | Wallet credential |
    | --- | --- | --- |
    | `x402` | `Authorization: Bearer ...` | `PAYMENT-SIGNATURE` |
    | `mpp` | `X-Lasso-Management-Key` | `Authorization: Payment ...` |

    Never send Bearer auth and `X-Lasso-Management-Key` together.
  </Step>
  <Step title="Confirm">
    `200` with `data.state=credited` is the durable receipt. x402 credit posts
    once Lasso verifies the successful Base receipt, without waiting for
    finality. `202` means the transfer is unresolved: honor `Retry-After`, then
    call `POST /api/v1/management/funding-operations/<id>/reconcile` on the same
    ID. Never sign or submit a second payment while one is pending.
  </Step>
</Steps>

`GET /api/v1/management/keys/<key_id>/balance` shows the current balance.

## Hand the app to its owner

```http
POST /api/v1/management/keys/<key_id>/claim-link
Authorization: Bearer <management credential>
```

Give the owner the returned `claim_url` privately; it expires in 10 minutes.
Claiming keeps the key, URL and premium scope, moves remaining purchased credit
to the account, and ends anonymous management. The owner grants later
management or funding separately in **Agent access**.

A claimed app can move to an active custom profile with
`PUT /api/v1/management/keys/<key_id>/binding`, keeping its secret and URL.

## Manage existing providers

An account owner connects an agent in one of two ways. They can create a
credential in **Agent access**, or approve the agent's request from
`POST /api/v1/management/access-requests` via the `approval_url` it returns.
Either way, the agent uses that credential as Bearer auth:

| Request | Purpose |
| --- | --- |
| `GET /api/v1/management/me` | Inspect delegated authority and expiry |
| `GET /api/v1/management/profiles` | List delegated profiles |
| `POST /api/v1/management/profiles` | Create a draft |
| `GET /api/v1/management/profiles/<id>/configuration` | Read configuration and its revision, without provider secrets |
| `POST /api/v1/management/profiles/<id>/plan` | Validate a proposed configuration |
| `PUT /api/v1/management/profiles/<id>/configuration` | Apply it |
| `POST /api/v1/management/profiles/<id>/activate` | Activate a configured draft |

A plan request for a single-chain draft:

```http
POST /api/v1/management/profiles/<id>/plan
Authorization: Bearer <owner-delegated management credential>
Content-Type: application/json

{
  "expected_revision": 0,
  "configuration": {
    "chains": [{
      "chain_id": 8453,
      "head_policy": "off",
      "providers": [
        {"id":"primary","url":"<existing primary RPC URL>"},
        {"id":"secondary","url":"<existing secondary RPC URL>"}
      ]
    }]
  }
}
```

Apply the same body with `PUT .../configuration` and a UUID. Chain and provider
lists are complete: omitted entries are removed. Omitting a retained provider's
URL keeps its stored secret. A provider probe is a bounded chain/head check that
consumes provider quota. It does not test archival or WebSocket support.
Suspension is permanent owner removal, not a pause.

## Integrate and evaluate

Change one endpoint using the codebase's existing secret manager, keep a
rollback, and verify a real application query before moving more traffic. The
[Base viem and ethers guide](/cloud/base-rpc-integration) shows a client
integration. Test historical reads, transaction sending and subscriptions
against their [workload behavior](/cloud/rpc-behavior).

A preview CLI wraps these flows for agents that prefer local state management.
It is not publicly distributed, and the HTTP API above is the supported path.
