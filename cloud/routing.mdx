# Routing

For every request, Lasso finds the providers in the profile that can serve it,
orders them by your strategy, and fails over to the next one when an error is
safe to retry. You choose the strategy per call site in the URL.

```bash
curl -sS "$LASSO_RPC_URL/fastest/base?include_meta=body" \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' \
  | jq '.lasso_meta | {strategy, candidate_providers, selected_provider, retries}'
```

## How a provider is chosen

1. **Find candidates.** Providers in the profile that serve the chain and
   transport. Known method gaps, history limits and range limits move a
   provider that can't serve the request to the back; Lasso never drops the
   last route.
2. **Order by health.** Providers with an open
   [circuit](/concepts/circuit-breakers) are skipped. Healthy providers come
   before rate-limited or recovering ones, and providers behind the requested
   block wait behind those at the head.
3. **Order by strategy.** Within each health group, your strategy sets the
   order.
4. **Send, and fail over.** A read that fails in a way that's safe to retry
   moves to the next provider, within one request deadline.

## Choose a strategy

| Strategy | What it does | Use it for |
|---|---|---|
| `load-balanced` | Spreads requests in random order across healthy providers, counting a provider once even when it serves both HTTP and WebSocket | Backends, indexers, quota spreading |
| `balanced-fast` (default on Premium) | Random order weighted toward providers with lower recent latency | User-facing reads |
| `fastest` | Tries the provider with the lowest recent latency for this kind of request first | Trading and latency-critical paths |
| `priority` | Tries providers in your Custom profile's configured order; use it on Custom profiles | A preferred primary with backups |

A URL without a strategy uses `balanced-fast` on Premium and `load-balanced` on
other profiles. `latency-weighted` is an alias of `balanced-fast`.

Latency is measured in the region serving you, per provider, transport and
kind of request (a family of related methods). Premium and Custom serve all
four strategies. `public`, payment fallback and free access serve
`load-balanced`, and `lasso_meta.strategy` reports what was used. On premium,
strategies [price differently](/cloud/serving-access-and-pricing).

## Failover on Lasso Cloud

| Situation | What happens |
|---|---|
| A provider times out or errors on a read | The next provider in the order is tried, within the request deadline |
| Every provider in the profile fails | The final JSON-RPC error returns inside an HTTP 200; check the body's `error`, not only the status. A profile never borrows providers from another pool |
| A signed transaction times out or gets a node-local rejection | The same bytes go to the next provider, up to three in total; sender faults stop there. See [transactions](/cloud/rpc-behavior#transactions) |
| A provider answers 429 | It moves behind healthy providers and returns to normal order when its cooldown ends |
| A provider keeps failing | Its circuit opens. After a cooldown, a trial request decides whether it returns |

Pin one provider with `<base>/provider/<name>/<chain>` to debug it. A pin has
no failover.

## When Lasso's own systems fail

Each node routes from its last-known keys, profiles and provider state, so a
database, billing or metering outage doesn't refuse requests. Changes made
during the outage take effect once the node can read them.

## Limits

- `load-balanced` spreads load across healthy providers, not evenly: if only
  one is healthy, it takes nearly every first attempt.
- `fastest` can concentrate traffic on one provider for one kind of request.
- Failover helps only when providers overlap on the method, history and chain
  you need. Two URLs on the same provider account can fail together.
