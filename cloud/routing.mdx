# Routing

For every request, Lasso finds the providers in the profile that can serve it,
orders them by your strategy, and fails over to the next one when an error is
safe to retry. You choose the strategy per call site in the URL.

```bash
curl -sS "$LASSO_RPC_URL/fastest/base?include_meta=body" \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' \
  | jq '.lasso_meta | {strategy, candidate_providers, selected_provider, retries}'
```

## How a provider is chosen

1. **Find candidates.** Providers in the profile that serve the chain and
   transport. Known method gaps, history limits and range limits steer the
   request away from providers that can't serve it; a provider is still tried
   when its support is unknown or every provider is impaired.
2. **Order by health.** Providers with an open circuit are skipped. Healthy
   providers come before rate-limited or recovering ones.
3. **Order by strategy.** Within each health group, your strategy sets the
   order.
4. **Send, and fail over.** A read that fails in a way that's safe to retry
   moves to the next provider, within one request deadline.

[Provider selection](/concepts/provider-selection) and
[circuit breakers](/concepts/circuit-breakers) describe each step in detail.

## Choose a strategy

| Strategy | What it does | Use it for |
|---|---|---|
| `load-balanced` (default) | Spreads requests in random order across healthy providers, counting a provider once even when it serves both HTTP and WebSocket | Backends, indexers, quota spreading |
| `latency-weighted` | Random order weighted toward providers with lower recent latency | User-facing reads |
| `fastest` | Tries the provider with the lowest recent latency for this kind of request first | Trading and latency-critical paths |
| `priority` | Tries providers in your Custom profile's configured order; use it on Custom profiles | A preferred primary with backups |

Latency is measured on the machine serving you, per provider, transport and
kind of request (a family of related methods). The
[routing strategies](/concepts/routing-strategies) concept page defines each
strategy precisely.

On `public`, and on any request served by payment fallback or free access,
every strategy is served as `load-balanced`. Premium and Custom serve all four.
Strategies price differently on premium; see
[serving access and pricing](/cloud/serving-access-and-pricing).

## Failover on Lasso Cloud

| Situation | What happens |
|---|---|
| A provider times out or errors on a read | The next provider in the order is tried, within the request deadline |
| Every provider in the profile fails | The final JSON-RPC error returns inside an HTTP 200. A profile never borrows providers from another pool |
| A signed transaction's response is lost | Lasso doesn't resend it. Look up the transaction hash before you do |
| A provider answers 429 | It moves behind healthy providers and returns to normal order when its cooldown ends |
| A provider keeps failing | Its circuit opens. After a cooldown, a trial request decides whether it returns |

Pin one provider with `<base>/provider/<name>/<chain>` to debug it. A pin has
no failover.

## When Lasso's own systems fail

Each node routes from its last-known keys, profiles and provider state. A
database, billing or metering outage doesn't refuse requests or fail health
checks; changes made elsewhere during the outage take effect once the node can
read them again.

## Limits

- Routing exhaustion arrives as a JSON-RPC error inside an HTTP 200 response.
  Check the body's `error`, not only the status.
- `load-balanced` doesn't promise an even split. If only one provider is
  healthy, it gets nearly every first attempt.
- `fastest` can concentrate traffic on one provider for one kind of request.
- Each region chooses providers from its own measurements.
- Failover helps only when providers overlap on the method, history and chain
  you need. Two URLs on the same provider account can fail together.
