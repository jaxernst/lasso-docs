# RPC method behavior

Lasso handles each method by whether it's safe to retry, depends on history,
or holds state on one provider. Use this table to plan each workload's rollout;
the sections below give the details.

| Workload | Failover | What your app owns |
|---|---|---|
| Current reads | Retried on another provider when safe | Chain reorgs and provider freshness differences |
| Historical state and logs | Steered toward providers known to serve that history | Splitting large `eth_getLogs` ranges; checkpoints |
| Trace and debug methods | Retried when safe; coverage varies by provider | Choosing providers that serve them |
| `eth_sendRawTransaction` | The same signed bytes go to up to three providers in turn; a sender fault stops at the first | Nonces, replacement, receipts, finality |
| HTTP filters | Not served | Use `eth_getLogs` or subscriptions |
| WebSocket `newHeads` and `logs` | Moved to another provider with bounded backfill | Reconnecting and resubscribing; durable checkpoints |

## Current reads

Methods such as `eth_blockNumber`, balances, receipts and most contract calls
fail over to another eligible provider when an error is safe to retry. Your app
still handles ordinary reorgs, and providers can differ by a block or two at
the head. For a latest block that never goes backwards on a Custom profile, set
[block protection](/cloud/custom-profiles#block-protection). For several reads
at the same block, use [read at one block](/advanced/read-at-one-block).

## Historical state and logs

Historical state, receipts and logs have separate coverage at each provider. A
provider that serves old logs may lack old state, and the reverse. Lasso infers
a request's age from its block selector and steers it toward providers known to
serve that depth. State reads by block hash go only to archival providers,
because a hash's age is unknown before dispatch.

`eth_getLogs` also has provider-specific range and result-size limits. When a
provider refuses a range as too large, Lasso returns `-32005` with
`data.code: "log_range_limit"` and a `next_action` to narrow the range; split
it in your app. When a provider refuses `eth_getLogs` for plan reasons, Lasso
tries the same query on another provider. Qualify your exact queries with
[indexer backfills](/cloud/indexer-backfills).

## Trace and debug methods

Trace namespaces are often plan-gated or client-specific. Test your exact
methods, parameters and timeouts through the profile you'll use. On a Custom
profile, Lasso learns which providers refuse a method and shows it in the
profile's knowledge.

## Transactions

`eth_sendRawTransaction` sends the same signed bytes to up to three providers
in turn, within one deadline. A rate limit, timeout, full pool, underpriced
replacement or unfamiliar rejection moves it to the next provider. A sender
fault stops at the first: nonce too low or too high, insufficient funds, an
invalid signature, a malformed transaction or invalid gas or fee limits. So
does a response saying the node already knows the transaction. A provider pin
sends to that provider only.

Before returning an error, Lasso looks the transaction up by hash once, and
returns the hash if the transaction is pending or mined. If the lookup can't
run in time, the error stands and the outcome is uncertain: resend the same
signed bytes, which is always safe, and reconcile by hash.

Final transaction errors carry `error.data.error_type: transaction_rejection`,
`retryable`, `next_action` and `request_id`; honor any `Retry-After`. A
successful response means a provider accepted the transaction, not that it was
included. Your app owns signing, nonces, replacement, receipts and finality.
Self-hosted RPC Core sends a transaction to
[one provider only](/api/supported-methods#signed-transaction-submission).

## HTTP filters

Lasso rejects `eth_newFilter`, `eth_newBlockFilter`,
`eth_newPendingTransactionFilter`, `eth_getFilterChanges`, `eth_getFilterLogs`
and `eth_uninstallFilter` with `-32601`. Filter IDs live on one provider and
can't follow a request to another. Use `eth_getLogs` for scans and WebSocket
subscriptions for real-time delivery. Self-hosted RPC Core forwards these
methods without failover; see [supported methods](/api/supported-methods).

## WebSocket subscriptions

Lasso shares upstream subscriptions across your clients and moves them to
another provider in the same profile when one fails, backfilling missed
`newHeads` and `logs` over HTTP and suppressing duplicates. Pending-transaction
subscriptions aren't served. The engine's behavior is documented in
[WebSocket subscriptions](/advanced/websocket-subscriptions).

## Limits

- Subscription recovery is bounded by a replay window and a deadline. When it
  can't complete, the socket closes with code 1011 rather than skip events;
  the client reconnects and resubscribes.
- Subscriptions don't move between profiles.
- Clients handle network disconnects, duplicates around a reconnect, and their
  own checkpoints for indexer-grade processing.
