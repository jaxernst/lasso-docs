# RPC method behavior

Lasso treats methods differently depending on whether they're safe to retry,
depend on history, or hold state on one provider. Use this table to plan each
workload's rollout and recovery; the sections below give the details.

| Workload | Failover | What your app owns |
|---|---|---|
| Current reads | Retried on another provider when safe | Chain reorgs and provider freshness differences |
| Historical state and logs | Steered toward providers known to serve that history | Splitting large `eth_getLogs` ranges; checkpoints |
| Trace and debug methods | Retried when safe; coverage varies by provider | Choosing providers that serve them |
| `eth_sendRawTransaction` | Identical signed bytes sent sequentially to up to three providers unless a sender fault stops sending | Nonces, replacement, reconciliation by hash, receipts, finality |
| HTTP filters | Not served | Use `eth_getLogs` or subscriptions |
| WebSocket `newHeads` and `logs` | Moved to another provider with bounded backfill | Reconnecting and resubscribing; durable checkpoints |

## Current reads

Methods such as `eth_blockNumber`, balances, receipts and most contract calls
fail over to another eligible provider when an error is safe to retry. Your app
still handles ordinary reorgs, and providers can differ by a block or two at
the head. For a latest block that never goes backwards on a Custom profile, set
[block protection](/cloud/custom-profiles#block-protection). For several reads
at the same block, use [read at one block](/advanced/read-at-one-block).

## Historical state and logs

Historical state, receipts and logs have separate coverage at each provider. A
provider that serves old logs may lack old state, and the reverse. Lasso infers
a request's age from its block selector and steers it toward providers known to
serve that depth. State reads by block hash go only to archival providers,
because a hash's age is unknown before dispatch.

`eth_getLogs` also has provider-specific range and result-size limits. When
Lasso recognizes that limit, it returns `-32005` with
`data.code: "log_range_limit"` and a `next_action` to narrow the range.
Split the range; Lasso doesn't split it or repeat the same query on another
provider. Some providers report a plan restriction on `eth_getLogs` as a
generic `-32600`; Lasso recognizes that and tries the unchanged query on
another eligible provider instead. Qualify your exact queries with
[indexer backfills](/cloud/indexer-backfills).

## Trace and debug methods

Trace namespaces are often plan-gated or client-specific. Test your exact
methods, parameters and timeouts through the profile you'll use. On a Custom
profile, Lasso learns which providers refuse a method and shows it in the
profile's knowledge.

## Transactions

`eth_sendRawTransaction` sends the same signed bytes sequentially to up to
three providers within one deadline. Rate limits, timeouts, pool capacity,
replacement underpricing and unfamiliar rejections can move to the next
provider. Known-transaction responses and sender faults stop submission
failover: examples include nonce too low or too high, insufficient funds,
invalid signatures, malformed transactions and invalid gas or fee limits.
A strict provider pin disables submission failover.

For a final routing error with a derivable transaction hash, Lasso attempts one
`eth_getTransactionByHash` lookup while the caller remains connected and the
original deadline and an available route permit it. A pending or mined object
returns the local hash only when its `hash` matches, case-insensitively.
Rejection wording alone never proves success. A failed or skipped lookup leaves
the error and can leave submission uncertain.

Final transaction errors carry `error.data.error_type: transaction_rejection`,
`retryable`, `next_action` and `request_id`; retain them and honor any available
`Retry-After`. Resend the identical signed bytes when retrying. A successful
response does not prove propagation, inclusion or finality. Your sender owns
signing, nonce allocation, replacement, hash reconciliation, receipts and finality.

RPC Core v0.5.1 retains its separate
[single-dispatch transaction contract](/api/supported-methods#signed-transaction-submission).

## HTTP filters

Lasso rejects `eth_newFilter`, `eth_newBlockFilter`,
`eth_newPendingTransactionFilter`, `eth_getFilterChanges`, `eth_getFilterLogs`
and `eth_uninstallFilter` with `-32601`. Filter IDs live on one provider and
can't follow a request to another. Use `eth_getLogs` for scans and WebSocket
subscriptions for real-time delivery. Self-hosted RPC Core forwards these
methods without failover; see [supported methods](/api/supported-methods).

## WebSocket subscriptions

Lasso shares upstream subscriptions across your clients and moves them to
another provider in the same profile when one fails, backfilling missed
`newHeads` and `logs` over HTTP and suppressing duplicates. Pending-transaction
subscriptions aren't served. The engine's behavior is documented in
[WebSocket subscriptions](/advanced/websocket-subscriptions).

## Limits

- Subscription recovery is bounded by a replay window and a deadline. When it
  can't complete, the socket closes with code 1011, and the client reconnects
  and resubscribes. Lasso never continues after a partial backfill.
- Subscriptions don't move between profiles. Payment changes and Custom
  access lapses follow the rules in
  [balance and payment fallback](/cloud/balance-and-fallback).
- Clients must handle network disconnects, duplicates around a reconnect, and
  their own checkpoints for indexer-grade processing.
