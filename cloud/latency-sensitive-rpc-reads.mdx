# Route latency-sensitive EVM RPC reads

For trading, quoting, wallets and other paths where every millisecond counts,
choose a latency strategy in the URL and measure it against your current
endpoint. Lasso measures each provider's recent latency on the machine serving
you, per kind of request, and orders providers by it.

```ts
const quotes = `${process.env.LASSO_RPC_URL}/fastest/base`;
const reads  = `${process.env.LASSO_RPC_URL}/balanced-fast/base`;
```

## Choose a strategy

| Strategy | First attempt | Trade-off |
|---|---|---|
| `fastest` | Tries the provider with the lowest recent latency for this kind of request first | Concentrates traffic on one provider; 2x the price on premium |
| `balanced-fast` | Random order weighted toward providers with lower recent latency | Spreads load while favoring fast providers; 1.5x the price on premium |
| `load-balanced` | Random order across healthy providers | Lowest price; no latency preference |

Health comes first: a provider with an open circuit is skipped whatever its
latency. [Routing strategies](/concepts/routing-strategies) defines each
strategy precisely. Latency strategies need `premium` or a Custom profile;
`public` serves `load-balanced` only.

## Measure your app's path

1. Pick one read method and a representative request mix.
2. Send it through your current endpoint and through Lasso from the same
   regions. Record success rate, p50, p95 and p99 end-to-end latency, error
   categories and head freshness.
3. Read `upstream_latency_ms`, `lasso_overhead_ms` and `selected_provider`
   from `?include_meta=body` to separate provider time from Lasso's time. See
   [routing evidence](/cloud/observability).
4. Repeat during a provider failure or throttle, where routing earns its keep.

A low mean latency alone doesn't show that your tail latency improved.

## Limits

- Latency is measured per provider, transport and kind of request (a family of
  related methods), per region; it isn't a per-method score.
- A provider without recent measurements isn't assumed fast or slow; it's
  tried after measured ones.
- Lasso's [routing overhead benchmark](https://lasso.sh/benchmarks/routing-overhead.html)
  measured 0.70 to 1.08 ms of added p95 latency in five short synthetic HTTP
  trials at 10,000 requests per second. That's engine overhead in isolation,
  not hosted capacity or internet latency.
- For several reads at one block, use [read at one block](/advanced/read-at-one-block);
  for a latest block that never goes backwards, use
  [block protection](/cloud/custom-profiles#block-protection). Neither
  guarantees finality.
