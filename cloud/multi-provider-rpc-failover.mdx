# Multi-provider RPC failover for production apps

Put several providers behind one standard JSON-RPC URL, and a provider's outage
or rate limit stops being your app's outage. Use this guide to confirm that
failover covers the failure you need to survive, using your app's own
requests. It works on Lasso's managed pool or on a
[Custom profile](/cloud/bring-your-own-rpc) over your own providers.

```bash
curl -sS "$LASSO_RPC_URL/load-balanced/base?include_meta=body" \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}' \
  | jq '.lasso_meta | {candidate_providers, selected_provider, retries}'
```

## What happens to a read

Lasso finds the providers that can serve the chain and method, orders them by
health and your strategy, and sends the request. If the provider fails in a way
that's safe to retry, such as a timeout, a 5xx or a rate limit, the next
provider is tried within the same request deadline. See [routing](/cloud/routing).

## What failover covers

| Work | On a provider failure |
|---|---|
| Reads: balances, calls, receipts, blocks, logs | Retried on the next eligible provider |
| Historical reads | Retried on the next provider, steered toward those known to serve that history |
| `eth_sendRawTransaction` | Sent once and never resent; reconcile by transaction hash |
| WebSocket subscriptions | Moved to another provider, with missed `newHeads` and logs backfilled within a bounded window |
| HTTP filters (`eth_newFilter`) | Not served; use `eth_getLogs` or subscriptions |
| A pinned provider (`/provider/<name>/`) | No failover |

## Run the trial

1. Pick a method your app already calls, such as `eth_blockNumber` or a
   contract read.
2. Send the same workload through the old endpoint and through Lasso. Compare
   correctness, error rate, latency and head freshness.
3. Read `lasso_meta` with `?include_meta=body` to see which provider served
   each request, and how many retries it took. See
   [routing evidence](/cloud/observability).
4. Force the failure you care about, such as throttling or taking down one of
   your own nodes, and confirm the app's requests keep succeeding.
5. Test writes and subscriptions separately, by their own rules above.

## Limits

- Failover only helps when another provider can serve the same method,
  history and chain. Two URLs on the same provider account, region or plan can
  fail together.
- A request has one deadline and a bounded number of attempts. When every
  attempt fails, you get the JSON-RPC error inside an HTTP 200 response.
- WebSocket recovery is bounded by a replay window and a deadline. When a
  recovery can't complete, the socket closes with code 1011, and the client
  reconnects and resubscribes. Keep your own checkpoint for indexer-grade
  processing.
