# Supported methods

Lasso routes a broad Ethereum JSON-RPC read surface, a conservative signed
transaction path, and a defined WebSocket subscription subset. Actual
availability still depends on the chain, profile, provider plan, transport,
history, and live capacity.

Method names are not assumed to be fungible. Lasso classifies execution safety
separately from provider capability:

- Reviewed replay-safe reads can use bounded failover.
- `eth_sendRawTransaction` receives one upstream dispatch.
- Unknown and vendor methods receive one dispatch unless reviewed policy marks
  them replay-safe.
- Stateful filter lifecycles and node-local signing methods are rejected.

Read [Ethereum JSON-RPC compatibility](/cloud/json-rpc-compatibility) for the
versioned standards target and precise compatibility terms.

The following methods are routable over HTTP and as unary WebSocket requests,
subject to provider capability and profile policy.

### Logs and network information

| Method | Notes |
| --- | --- |
| `eth_getLogs` | Stateless log query. Provider block-range and result-size limits apply. |
| `eth_chainId` | Served locally after route authentication and chain resolution. |
| `eth_syncing` | Upstream pass-through. |
| `net_version` | Upstream pass-through. |
| `web3_clientVersion` | Upstream pass-through. |
| `web3_sha3` | Upstream pass-through. |

Node-operator methods such as `net_listening`, `net_peerCount`, and
`eth_protocolVersion` may be withheld by hosted providers. Their absence does
not imply that ordinary application reads are unavailable.

## Evolving reads and extensions

Lasso's reviewed registry includes evolving reads such as
`eth_getBlockReceipts`, `eth_capabilities`, `eth_config`,
`eth_getStorageValues`, and `eth_simulateV1`. These methods are replay-safe in
Lasso's execution policy, but remain capability-routed because deployment,
fork, cost, and access differ across providers.

Debug, trace, transaction-pool, bundler, and chain-specific namespaces may also
be forwarded when an upstream supports them. Lasso presents them as extensions,
not as universally supported Ethereum methods.

<Warning>
Debug and trace calls can be expensive or plan-gated. Test the exact method,
parameters, provider plan, and timeout before depending on one in production.
</Warning>

Unknown methods remain forward-compatible. They receive one upstream dispatch
and no cross-request affinity guarantee unless a reviewed contract states
otherwise.

## Signed transaction submission

`eth_sendRawTransaction` is routable. Lasso sends the signed bytes to one
selected upstream under one deadline and does not retry or fan out after
dispatch. A lost response may still mean the upstream accepted the transaction.

Your application remains responsible for signing, nonce allocation,
replacement, transaction-hash reconciliation, receipt tracking, and finality.

## WebSocket subscriptions

The launch subset supports these exact forms over WebSocket:

| Method | Parameters | Recovery |
| --- | --- | --- |
| `eth_subscribe` | `["newHeads"]` | Bounded block replay and reorg repair. |
| `eth_subscribe` | `["logs"]` or `["logs", filter]` | Bounded log replay, retained orphan removal, and duplicate suppression. |
| `eth_unsubscribe` | `[subscriptionId]` | Removes a subscription owned by the downstream connection. |

Subscription IDs authored by Lasso are lowercase hexadecimal quantities.
Trailing arguments and unsupported subscription kinds return invalid-params
errors. A `logs` filter must be an object; the selected upstream remains
authoritative for its field-level validation.

Pending-transaction and transaction-receipt subscription kinds are not part of
the launch subset. Recovery that exceeds the configured time, ancestry, replay,
or memory bounds terminates the affected client explicitly.

HTTP requests for `eth_subscribe` or `eth_unsubscribe` return a method error
with a WebSocket hint.

## Rejected methods

### Provider-local HTTP filters

Lasso rejects the following methods locally with `-32601` across HTTP, batch
items, unary WebSocket requests, and explicit-provider routes:

- `eth_newFilter`
- `eth_newBlockFilter`
- `eth_newPendingTransactionFilter`
- `eth_getFilterChanges`
- `eth_getFilterLogs`
- `eth_uninstallFilter`

Their filter IDs belong to one upstream. Lasso does not advertise a sticky
affinity lifecycle for them. Use `eth_getLogs` for historical scans or the
supported WebSocket subscription subset for real-time delivery.

### Wallet, signing, and node-local account methods

Lasso does not hold user signing keys or provide node-local account management.
It rejects methods such as:

- `eth_accounts`
- `eth_sign`
- `eth_signTransaction`
- `eth_sendTransaction`
- `personal_sign`
- mining and work-submission methods

Use a wallet or application signer, then submit the resulting signed bytes with
`eth_sendRawTransaction`.

## Standards status

| Interface | Lasso posture |
| --- | --- |
| JSON-RPC 2.0 | Lasso validates client envelopes and authors conformant local responses. |
| EIP-1898 | Object block selectors support `blockNumber` or `blockHash`, with `requireCanonical` valid only for `blockHash`. |
| EIP-234 | `eth_getLogs.blockHash` is mutually exclusive with `fromBlock` and `toBlock`. |
| EIP-1186 | `eth_getProof` is routable subject to history and provider capability. |
| EIP-1474 | Used as an influential source for value and error conventions; it is Stagnant, not a complete Final baseline. |
| Pinned execution APIs | Reviewed at commit `739f9e00806003d2204adca7595f704849b9be30`; inclusion does not imply universal provider availability. |

Successful upstream result objects pass through without field-by-field
rewriting. This preserves additive fork fields and chain-specific extensions.

## HTTP batches

Lasso supports JSON-RPC batches over HTTP. Each item is validated and routed
independently. Valid notifications produce no response item, duplicate IDs are
preserved, and the exact ID type and value are echoed. Use unique IDs for
unambiguous client correlation.

WebSocket batching is not part of the advertised launch surface.
