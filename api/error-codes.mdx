---
title: Error codes
description: RPC Core's JSON-RPC errors, what it returns when no provider can serve a request, and when a retry is safe.
---

Lasso Cloud's errors are in [response signals and errors](/cloud/reference/signals-and-errors).
Core preserves a valid, request-correlated upstream JSON-RPC error's `code`,
`message`, and optional `data` when the upstream HTTP response is 2xx. An error's numeric code alone does not prove
which provider failed or whether repeating the operation is safe.

## JSON-RPC envelope

An error response has `jsonrpc`, `id`, and an `error` object with an integer
`code` and string `message`. `data` is optional and its shape depends on the
source of the error. A valid notification has no response; an all-notification
batch returns HTTP 204. Core routes batch items independently.

| Code | Meaning | Core example |
| --- | --- | --- |
| `-32700` | Parse error | Malformed JSON. |
| `-32600` | Invalid Request | An invalid request object or empty/oversized batch. |
| `-32601` | Method not found or unsupported on this transport | `eth_subscribe` over HTTP. |
| `-32602` | Invalid params | A method's parameters are invalid. |
| `-32603` | Internal error | An error reported by Lasso or preserved from an upstream. |
| `-32000` | Server error | Routing exhausted its eligible attempts. |
| `-32005` | Limit exceeded | Every eligible provider's [outbound request budget](#outbound-request-budget) is spent, the providers rate limited the request or reported a spent plan allowance ([details](#rate-limits-and-spent-allowances)), an `eth_getLogs` range a provider refused, or Lasso's response-size cap; see [large queries](#large-eth_getlogs-queries). |
| `-32006` | Capability refusal | No provider could serve a one-block `eth_getLogs` query, or a gateway refused the request with HTTP 406; see [one-block queries](#one-block-eth_getlogs-queries) and [gateway refusals](#gateway-refusals). |
| `-32008` | Local capacity | Lasso had no local transport capacity before dispatch; retry a replay-safe request. |

These are categories, not a promise that every example uses exactly that code.
For instance, a valid upstream error can carry its own server-defined code.
Core does not issue Cloud API-key, account-quota, or strategy-entitlement errors;
protect incoming Core traffic at your [deployment boundary](/api/authentication).

## HTTP subscriptions

The released controller rejects `eth_subscribe` and `eth_unsubscribe` over HTTP
with `-32601` and a WebSocket route hint. Connect through
[WebSocket endpoints](/api/websocket-endpoints) for subscriptions.
Core can forward provider-local HTTP filter methods when capability policy
permits, with one dispatch and no cross-request affinity. Cloud rejects its
[documented filter lifecycle](/cloud/rpc-behavior#http-filters) locally.

## Core routing exhaustion

When no eligible attempt can serve a request, Core returns a JSON-RPC
`-32000` error over **HTTP 200**, preserving the request ID. `data` has
`reason`, `retry_after_ms`, and `upstream_attempts`. `retry_after_ms` can be
non-null only for `no_eligible_providers`.

| `reason` | Meaning | Next action |
| --- | --- | --- |
| `no_eligible_providers` | Configured routes are currently unavailable. | Honor a present `retry_after_ms` for a replay-safe request. |
| `archive_required` | The request needs declared archival support. | Configure and qualify an archival provider. |
| `transport_unavailable` | No eligible route supports the requested transport. | Configure that transport or change the request. |
| `no_providers_configured` | The profile has no provider for the chain. | Correct the profile. |
| `providers_excluded` | Every provider was explicitly excluded. | Review the override or exclusion. |
| `routing_configuration_changed` | The route changed during selection. | Repeat a replay-safe request against the current configuration. |

This serializer fixture uses a fixed retry interval; the live interval depends
on current circuit state:

```json
{
  "error": {
    "code": -32000,
    "data": {
      "reason": "no_eligible_providers",
      "retry_after_ms": 5000,
      "upstream_attempts": 0
    },
    "message": "No available channels for method: eth_blockNumber. All circuits open, retry after 5s"
  },
  "id": "client-request-42",
  "jsonrpc": "2.0"
}
```

The shape comes from the released
[controller regression](https://github.com/jaxernst/lasso-rpc/blob/v0.8.6/test/lasso_web/controllers/rpc_controller_test.exs)
and [request pipeline](https://github.com/jaxernst/lasso-rpc/blob/v0.8.6/lib/lasso/core/request/request_pipeline.ex).
When every upstream a request reached rejected the method, Core returns that
upstream's `-32601` with its message and data instead. If another outcome
occurred, such as a provider failure, quota exhaustion or timeout, you get that
outcome's error or the availability error above. An `eth_getLogs` request that
any provider refused as too wide returns the
[range error](#large-eth_getlogs-queries) instead, whatever happened after it.

Request [metadata](/observability/request-metadata) can show recorded attempts
when available. It does not promise an exhaustive provider diagnostic schema.

## Outbound request budget

When every eligible provider's
[`request_budget`](/configuration/providers#outbound-request-budget) is spent,
Lasso sends nothing and returns `-32005` over HTTP 200:

```json
{
  "jsonrpc": "2.0",
  "id": "client-request-42",
  "error": {
    "code": -32005,
    "message": "Upstream request budget exhausted",
    "data": {
      "reason": "upstream_request_budget_exhausted",
      "retry_after_ms": 340
    }
  }
}
```

`retry_after_ms` is the time until the earliest provider's budget refills; no
request reached an upstream. Wait that long and retry. When some attempts reached a provider
and failed, the response follows the ordinary rules above, and a range refusal
still returns the [range error](#large-eth_getlogs-queries). With
`include_meta`, `budget_refusals` lists the providers Lasso skipped.

## Large `eth_getLogs` queries

Core turns a recognized provider block-range or result-size limit, or its own
bounded response-size rejection, into one JSON-RPC error:

```json
{
  "jsonrpc": "2.0",
  "id": "client-request-42",
  "error": {
    "code": -32005,
    "message": "eth_getLogs result exceeds a range or size limit; reduce the block range",
    "data": {
      "reason": "log_range_too_large",
      "action": "reduce_block_range",
      "max_block_range": 2000
    }
  }
}
```

`max_block_range` is the smallest
[`capabilities.limits.max_block_range`](/configuration/capabilities) among the
providers that refused the range. It appears only when you configured that limit;
otherwise the error carries `reason` and `action` alone. Lasso never takes the
number from provider error text.

Split the query into spans no wider than `max_block_range`, or narrower spans
when it is absent, and collect the results in your application. Lasso does not
split the query for you. An upstream range or result-size refusal fails over to
another eligible provider within the request budget, and a successful fallback
returns its result. When no provider completes the request, Core returns this
error even if later attempts timed out or were rate limited, and without their
retry delays: waiting does not fix a range refusal, so retrying the same range
fails again. Core's own bounded response-size rejection is terminal. Other
malformed filter arguments keep their original error.

### One-block `eth_getLogs` queries

A query for exactly one block, with equal `fromBlock` and `toBlock` or a
`blockHash`, can't be narrowed. When a provider refuses one, usually because it
no longer holds that history, Lasso tries the other providers. If none serves
it, Core returns a capability refusal with no narrowing advice:

```json
{
  "jsonrpc": "2.0",
  "id": "client-request-42",
  "error": {
    "code": -32006,
    "message": "This provider cannot serve eth_getLogs for this block; history may not be retained"
  }
}
```

Add a provider that retains that block's history, or query a more recent block.
A query from block N through N+1 covers two blocks and still gets range advice.

## Rate limits and spent allowances

An upstream answers HTTP 429 when it throttles and HTTP 402 when its plan
allowance is spent. Lasso handles both the same way: it moves the request to
the next eligible provider, holds the refusing provider back for
[the wait it asks for](/concepts/circuit-breakers#rate-limit-cooldowns), and
never counts the refusal toward its circuit. When every provider the request
reached refused it this way, Core returns `-32005` over HTTP 200. `data` carries
only `retry_after_ms`, when the provider asked for a wait, and none of the
upstream's response body. Wait that long before retrying a replay-safe request.

## Gateway refusals

Some gateways refuse a method with HTTP 406 and a non-JSON-RPC body, such as an
HTML page, before their RPC handler runs. Lasso treats that as a refusal of this
request only: it tries the next eligible provider and leaves the refusing
provider's circuit closed, so its other methods keep serving. When no provider
serves the request, Core returns a capability refusal with no upstream body:

```json
{
  "jsonrpc": "2.0",
  "id": "client-request-42",
  "error": {
    "code": -32006,
    "message": "Provider refused the request (HTTP 406)",
    "data": {"status": 406}
  }
}
```

A 406 that carries a JSON-RPC error is classified by that error's code. Add a
provider that serves the method, or send the request to a route that has one.

## Upstream errors and retry safety

An upstream can return a JSON-RPC error body with any HTTP status, but the
Core HTTP client validates and preserves that body only for a 2xx response.
HTTP status decides first: 429, 402, 408, other 4xx, and 5xx statuses are transport
or upstream-status failures, even when their body contains a JSON-RPC error, so
a replay-safe read moves to another provider. A 429 or 402 is always a
[rate limit](#rate-limits-and-spent-allowances), and a 406 whose body isn't a
JSON-RPC error is a [gateway refusal](#gateway-refusals). A structurally valid, request-correlated error in a 2xx response keeps
its provider code and wording. Gateway text, HTML, and malformed 2xx envelopes
are not authoritative JSON-RPC errors.

Core can fail over reviewed replay-safe reads within their dispatch budget and
absolute deadline. Signed transaction submission receives one upstream
dispatch; with a chain's
[transaction providers](/configuration/profiles#transaction-providers), a
registered send goes as the same bytes to up to three of them in turn. A lost
response may follow acceptance. Reconcile its hash before deciding whether to
rebroadcast. Stateful filters and unknown methods have different
limits. See the [method-safety contract](/api/supported-methods) before adding
application retries.

## WebSocket closure

The released socket closes with code `1002` after two unanswered server
heartbeats and `1011` when subscription continuity is exhausted. Other
network, server, and proxy closures are possible. Reconnect, recreate the
subscription, and use an application checkpoint to recover events missed while
the client was disconnected. See [connection lifecycle](/api/connection-lifecycle).
